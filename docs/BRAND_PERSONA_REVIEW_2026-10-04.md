## 1. 1차 진단의 판단 중 실측으로 «확정» 된 것

### ✅ 약점 1 — 북극성이 비어 있다 (사실)

`docs/BRAND_PERSONA.md` 4행은 「금지선과 북극성은 **이 문서 1장**을 따른다」고 적었는데,
1장의 제목은 **「왜 바꾸나 — 기존 퍼소나 진단」** 이고 내용은 기존 퍼소나 진단표·후보 3개 비교·유지/변경 목록뿐이다.
**북극성 문장은 문서 어디에도 없다.** 1차 진단이 의심한 「DESIGN_SYSTEM.md를 가리켰을 가능성」도 아니다
(4행이 두 문서를 명시적으로 나눠 가리킨다).

→ 1차 진단의 보완점 1은 그대로 유효하며, **가장 먼저 해야 할 일이 맞다.**

### ✅ 약점 3 — 연속 기록 이정표가 원칙 3과 충돌한다 (사실, 그리고 대안이 이미 코드에 있다)

`src/lib/gamification.js` 실제 값:

```js
STREAK_PRESETS = { short: [3, 7], medium: [7, 14], long: [7, 14, 30] }   // 기본 medium
CUMULATIVE_MILESTONES = [50, 100]                                        // 이미 존재
```

마법사 기본값이 `streak_preset: medium` 이라 **연속 7일·14일이 기본으로 켜진다.** 1차 진단의 지적이 맞다.

→ ⚠️ **다만 1차 진단이 몰랐던 것**: 누적 이정표(`CUMULATIVE_MILESTONES`)가 **이미 구현되어 있다.**
보완점 6의 「10번째·25번째 인증으로 바꾸라」는 제안은 새 기능 개발이 아니라 **기본값과 노출 비중을 바꾸는 일**이다.
비용이 1차 진단이 가정한 것보다 훨씬 작다. 우선순위를 올릴 만하다.

### ✅ 위기 5 — 한국 전용 값이 코드에 박혀 있다 (사실, 위치 확정)

- `109`는 **6곳**에 하드코딩 — `src/components/program/MoodCheck.jsx`(면책 문구 본문) + `src/lib/quizLibrary.js` 5곳(퀴즈 해설·링크 `129.go.kr/109`)
- **i18n 라이브러리가 설치되어 있지 않다.** `package.json` 의존성에 i18n/intl/lingui 계열 0건 → 문자열은 전부 JSX 안에 한국어로 하드코딩
- 퀴즈 문항에는 「전우 · 간부 · 병영생활 전문상담관 · 군종」 같은 **특정 조직 전용 용어**까지 들어 있다

→ 1차 진단의 「지금이 가장 비용이 적다」는 판단은 맞지만, **실제 비용은 더 크다.**
문자열 리소스 분리 자체가 안 되어 있어 보완점 8(상황 ID 리소스화)은 「문자열 하나 바꾸기」가 아니라 **구조 작업**이다.

### ✅ 약점 6 — 8장 표가 갱신되지 않았다 (부분 사실)

`BRAND_PERSONA.md` 179행에는 마이그 277 적용·검증 주석이 **이미 들어가 있다.**
그러나 **316행의 8장 점검표 행은 여전히 「마이그 167 — 누가 보냈는지 이름이 없음」으로 남아 있다.**
→ 같은 문서 안에서 두 곳이 어긋난다. 1차 진단의 지적은 유효하되 「미수정」이 아니라 **「한 곳만 수정」** 이 정확하다.

### ✅ 강점 1 — 운영자를 앞에 세우는 결정이 제품까지 갔다 (사실)

마이그 277(2026-10-01 프로덕션 적용) 원문 확인:
- `title` = 프로그램 이름(20자 초과 시 19자+…)
- `body` = `운영자 닉네임 + ": " + 메시지`
- 닉네임이 비면 「운영자」, 프로그램명이 비면 「도담」
- 푸시도 같은 title/body를 쓴다(178 트리거) → **알림과 푸시가 동시에 바뀜**

→ 1차 진단의 평가가 정확하다. 이 항목은 도담의 가장 단단한 근거다.

## 2. 실측으로 «악화» 된 것 — 우선순위를 올려야 함

### 🔴 위기 2 — 운영자는 이미 참여자의 기분 기록을 «개인별로» 볼 수 있다

1차 진단은 「운영자가 참여자의 무엇을 볼 수 있는지는 어디에도 정해져 있지 않습니다」라고 썼다.
실제로는 **정해져 있고, 열려 있다.**

```sql
-- supabase/migrations/20260628_137_mood_logs.sql
CREATE POLICY mood_logs_owner_read ON public.mood_logs
  FOR SELECT TO authenticated
  USING (EXISTS (SELECT 1 FROM programs p
                 WHERE p.id = mood_logs.program_id AND p.owner_id = auth.uid()));
```

- 주석은 「운영자: 자기 프로그램 기록 조회 **(통계)**」라고 적혀 있으나, **정책에는 집계 제한도 최소 인원 억제도 없다.**
  행 단위로 `user_id` 와 함께 전부 읽힌다. 2026-06-28 이후 이 정책을 수정한 마이그레이션도 없다.
- 인증 사진도 동일하게 운영자 전체 열람이다(마이그 018 `view own or own program verifications`).
- 금연 기록·설문 응답의 열람 범위는 ❓ 별도 확인 필요(설문은 전용 정책을 찾지 못했다).

**왜 더 위험한가**: 기분 체크는 개인정보 보호법상 **민감정보**에 해당할 소지가 크고,
도담의 실사용 1위 프로그램은 참여자 77명 규모의 단체형이다. 즉 「회사·기관이 내 기분 기록을 본다」가
가정이 아니라 **현재 동작**이다. 앱 어디에도 이 사실을 참여자에게 알리는 고지가 없다.

→ 1차 진단의 보완점 3은 「정하자」가 아니라 **「이미 열린 것을 닫거나, 닫지 않을 거면 고지하자」** 로 바뀌어야 한다.
출시 전 결정 1순위로 올릴 것을 권한다. ❓ 법률 검토는 여전히 필요하다.

### 🔴 위기 4 — 프로그램 기간이 습관 형성 기간의 절반이다

1차 진단은 「도담 프로그램의 실제 평균 기간은 확인이 필요합니다」라고 남겼다.
**중앙값 32일**이다. 1차 진단이 인용한 Lally 외(2010)의 중앙값 약 66일의 **절반**이고, 1개월 이하가 15건 중 8건이다.

→ 「건강 기여」를 말하려면 **프로그램 종료 후를 설계해야** 한다는 1차 진단의 지적이 수치로 뒷받침된다.
보완점 6의 종료 문구(「혼자 이어서 기록하기」)와 「프로그램을 넘어 이어지는 개인 기록」이
나중 과제가 아니라 **지금 전략의 중심**이 되어야 한다는 뜻이다.

## 3. 실측으로 «정정» 되어야 하는 것 — 1차 진단의 전제가 틀림

### ⚠️ 기회 4 / 보완점 6 — 앱에 상품·보상 설정 기능이 «없다»

1차 진단은 「보상을 1등 몇 명 대신 기준을 채운 다수로 추천하라」, 「상품 안내 문구는 이렇게 쓰라」고 제안했다.
그러나 **프로그램 마법사와 미션 생성 어디에도 상품·경품 설정 UI가 없다.** 코드 검색 결과 0건이다.

→ 상품은 현재 **앱 밖(카톡 공지·운영자 구두 안내)에서 굴러간다.**
따라서 그 제안들은 「문구 수정」이 아니라 **기능 신설**이다. 1차 진단은 이를 문구 과제로 분류했는데 재분류가 필요하다.
내부 전략 메모는 상품을 **「획득 미끼, 본질 아님」** 으로 이미 결론 냈으므로,
**기능을 만들지 않기로 한 결정일 수도 있다.** 다음 검토자는 이 둘 중 무엇인지부터 물어야 한다.

### ⚠️ 기회 4 — 「랭킹 기본 끄기」 제안은 현재와 정반대

마법사 실제 기본값(`Step2Type.jsx:560`)은 랭킹 **기본 ON**, 시상대 기본 OFF다.
그리고 실제로 게시 프로그램 **15개 중 13개가 랭킹을 켜고 있다.**

→ 「랭킹 기본 끔」은 작은 기본값 변경이 아니라 **현재 제품 정체성의 전환**이다
(게이미피케이션 타입도 RANKING 14 / GARDEN 1). 1차 진단이 가볍게 제안했지만 실제로는 큰 결정이다.

### ⚠️ 위기 4의 인용 근거 — 「인증 하루 1건」 신호는 이미 철회된 수치

1차 진단에는 없지만, 다음 검토자가 내부 메모를 받으면 마주칠 함정이라 적어 둔다.
2026-09-07 전략 메모의 「참여자 70명인데 인증 하루 약 1건」이라는 리텐션 반증 신호는
**2026-09-16에 정정됐다.** 해당 프로그램의 미션 활성 창이 하루뿐이었던 **운영자 의도**였고,
창이 열린 날 반나절에 76명 중 11명(14%)이 인증했다. 이 수치를 리텐션 실패의 증거로 쓰면 오진이다.

### ⚠️ 약점 2 — 전략 문서는 «있다». 다만 퍼소나 문서와 연결되어 있지 않다

1차 진단은 「Shopify 전략과 가치 3층 프레임이 별도 문서로 있다면 연결만 해도 메울 수 있습니다」라고 했다.
**둘 다 존재한다.** 핵심만 옮기면:

- **Shopify 전략(2026-08-14)**: 도담은 개인 건강앱이 아니라 «남의 건강 여정을 운영하는 사람의 도구».
  경쟁 회피 근거는 전국민 대상 무료 공공앱과 정면으로 붙으면 진다는 판단. 살길은 조직별 브랜드 운영.
- **가치 3층(2026-09-07)**: 획득(상품=미끼) → 유지(인증·응원) → **보고(최고 지불의사)**.
  보고 레이어가 진통제이며, 현재 종료 리포트는 아직 「데이터 요약」 수준이라는 자체 평가가 있다.
- **지불 의사**: 인증 취합 단독으로는 돈이 안 된다(비타민). 사는 이유는 **돈·규모·전문성·반복**.
- **운영자 6고통 감사**: 기능은 6개 다 있고 문제는 「쉬움 + 깊이」. 가장 약한 곳은 **이탈 관리**,
  최대 마찰은 **개설 14~15화면**이었다(이후 미션 만들기 6→5단계로 축소, 이탈 리마인드 기능 추가).

→ 1차 진단의 「포지셔닝이 없다」는 지적은 **퍼소나 문서에 없다**는 뜻으로 좁혀야 한다. 전략 자체는 있다.
문제는 **전략과 퍼소나가 서로를 참조하지 않는다**는 것이다.

### ⚠️ 위기 1 — 경쟁사 조사는 이미 되어 있고, 결론이 1차 진단과 다르다

2026-09-22 조사(Everfit / Circle / TrueCoach):

| | Everfit | Circle | TrueCoach |
|---|---|---|---|
| 규모 | 코치 32만 | 팀 페리스 등 | 트레이너 2만 |
| 과금 축 | 참여자 수 $0.72~3.17/인 | 정액 + 거래 수수료 0.5~2% | 참여자 수 구간제 |
| 브랜드 앱 | Enterprise 전용 | Circle Plus 별도가(+$200~400/mo) | 표기 불일치(미확인) |

**결론 세 가지가 1차 진단의 프레임을 바꾼다.**
1. 「프로그램 단위 브랜딩」은 신규 아이디어가 아니라 **이미 비싸게 팔리는 상품**이다. 차별점은 존재가 아니라 **가격**이다.
2. 셋 다 **영어 전용·1:1 코칭 중심**이다. 보건소·기업·학교의 «단체 건강증진 프로그램»은 비어 있다.
3. 🔴 **가장 큰 격차는 운영자가 «돈을 받는» 기능이다.** 셋 다 결제·구독·패키지 판매가 내장이고 거기서 수수료를 번다.

## 5. 실측을 반영한 우선순위 재배치

1차 진단의 「이번 주에 할 세 가지」를 실측에 맞춰 고친다.

**1순위 — 기분 기록 열람 범위 결정 (🔴 제품 결정, 법률 동반)**
1차 진단은 뒤쪽으로 다뤘으나, 이미 열려 있고 실사용 1위 프로그램이 단체형이라 가장 급하다.
닫을지(정책 수정 + 운영자 통계는 집계만), 열어 둘지(참여자 고지 + 동의)를 먼저 정한다.

**2순위 — 북극성·포지셔닝 한 장 (문서)**
전략은 이미 있으므로 **새로 쓰는 게 아니라 연결하는 일**이다.
Shopify 전략·가치 3층·경쟁사 조사·상표 조사를 퍼소나 1장 앞에 묶고, 미션 한 줄과 신념 3문장만 새로 쓴다.

**3순위 — 연속 → 누적 이정표 전환 (코드, 비용 작음)**
`CUMULATIVE_MILESTONES` 가 이미 있으므로 기본값과 노출 비중 조정 수준이다. 원칙 3과 제품을 일치시키는 가장 싼 수단.

**4순위 — 109를 설정값으로 분리**
단, i18n 구조가 없으므로 「문자열 하나」가 아니다. 최소한 상수 한 곳으로 모으는 것부터.

**보류 권고 — 상품 관련 문구 작업**
기능 자체가 없다. 상품을 앱에 넣을지가 먼저 결정되어야 한다(전략 메모는 「본질 아님」으로 기운다).

## 7. 3차 진단 이후 추가 실측 (2026-10-04 저녁)

3차 진단이 「이번 주에 실측하라」고 요구한 항목 중 DB 로 답할 수 있는 것을 측정했다.
**결과적으로 2차 개정판(이 문서 2장)의 과장 하나가 드러났다. 먼저 정정한다.**

### 🔵 정정 — 기분 기록 노출 «규모» 는 매우 작다

| 측정 | 값 |
|---|---|
| mood_logs 총 행 수 | **2행** |
| 기록한 사람 | **2명** |
| 해당 프로그램 | **1개** |

2차 개정판은 이 정책을 🔴 1순위로 올리면서 「회사·기관이 내 기분 기록을 본다가 현재 동작」이라고 썼다.
**정책이 열려 있다는 사실은 그대로지만, 실제 노출된 기록은 2건이다.**
3차 진단의 지적(근거 (나) — 행 수를 재지 않았다)이 옳았다.

→ 조치의 방향은 바뀌지 않는다(닫는 게 맞다). **다만 이유가 바뀐다.**
「사고가 났으니 급하다」가 아니라 **「아직 아무것도 쌓이지 않았을 때 닫는 것이 가장 싸다」** 이다.
열려 있던 기간에 대한 참여자 고지도, 대상이 2명이라 부담이 작다.

### 🔵 정정 — 「심사 자동화는 절반에만 해당」은 틀렸다

| 기준 | 자동 승인 | 운영자 심사 |
|---|---|---|
| 미션 수 | 18 / 30 (60%) | 12 / 30 (40%) |
| **인증 건수** | **274 / 417 (66%)** | **143 / 417 (34%)** |

2차 개정판은 미션 수로 세어 「절반에만 해당」이라 썼다. 건수로는 **3분의 2가 자동**이다.
3차 진단의 지적이 옳다.

**반려 22건의 출처**: 운영자 심사 미션 21건 + 자동 승인 미션 1건
→ 수동 심사분 반려율 **21/143 = 14.7%**. 전체 반려율(5.3%)의 세 배다.
3차 진단이 예측한 그대로다.

### ✅ 기각 — RLS 가 꺼져 API 로 읽히는 상태는 아니다

익명 키(anon)로 5개 테이블을 직접 호출한 결과 **전부 빈 배열**이 돌아왔다.
verifications 에 417행이 실재하는데도 0행이 반환되므로, **RLS 가 정상 작동한다**는 증거다.

| 테이블 | 익명 호출 결과 |
|---|---|
| mood_logs / survey_responses / verifications / users / programs | 200, 빈 배열(차단) |

→ 3차 진단이 우려한 세 상태 중 **「RLS 가 꺼져 프로그램 경계 없이 읽히는 상태」는 아니다.**
남은 과제는 «익명 차단»이 아니라 «운영자 범위»다.

### 🔴 새로 드러난 것 — 누적 이정표 [50, 100] 은 데이터로 기각된다

사람별 **승인** 인증 수 분포(66명):

```
87, 34, 30, 27, 26, 20, 12, 11, 10, 7, 6, 4, 3×30, 2×18, 1×12
```

| 기준 | 도달자 |
|---|---|
| 100회 이상 | **0명** |
| 50회 이상 | **1명** |
| 10회 이상 | 9명 (13.6%) |
| **중앙값** | **3회** |

→ 현재 기본 이정표 `CUMULATIVE_MILESTONES = [50, 100]` 은 **66명 중 1명만 절반을 통과**했고
100에는 아무도 닿지 못했다. 3차 진단의 결정 5(5·10·20으로 교체)가 실측으로 입증된다.

### 🔴 새로 드러난 것 — 보고할 «결과» 자체가 아직 없다

위 분포의 진짜 의미는 이정표가 아니다.

> **참여자 1인당 승인 인증 중앙값이 3회다.**

가치 3층에서 지불의사가 가장 높다고 본 **「보고」 레이어는 이 숫자 위에 선다.**
중앙값 3회로는 어느 기관에도 제출할 성과가 나오지 않는다.

→ **순서 제안**: 「누구에게 약속할지」를 정하기 전에 **「약속할 결과가 나오는가」** 를 먼저 풀어야 한다.
분기(단체/코치)를 먼저 고르면, 어느 쪽을 골라도 보여 줄 실적이 없다.
